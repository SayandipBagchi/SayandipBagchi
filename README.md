I write the specs, and I build the tooling that makes the specs cheaper to get right. That is mostly retrieval systems, agents and operator tooling, so a product team of six can work like a larger one. Four of those agents run inside my own team: one that derives a card programme's real stage ladder from live data rather than assuming it and builds the dashboard suite on top, one that codes voice-of-customer themes from contact-centre transcripts, one that lets a PM ship copy and config changes to a programme's web app without an engineering ticket and escalates anything that genuinely needs one, and a knowledge base over product documentation. All four work the same way: derive the contract from the data, keep the output schema strict, and put a human gate in front of anything that writes.

## How I think about building with AI

- **Boring before clever.** Better chunking and a reranker beat HyDE and graph indexes on most corpora. Coordinate clicks beat clever DOM heuristics on Atlaskit. Reach for the sophisticated thing after the boring thing has hit a measured ceiling, not before.
- **Taste is the speed advantage now.** The models are good enough that the bottleneck has moved. Generating ten plausible options is free; knowing which one is worth keeping is not, and that judgement is the part no framework hands you. Most of what looks like prompting skill is someone with a clear idea of what good looks like, rejecting faster.
- **The schema of the output is the product.** "Tell me what's broken" produces unreviewable noise. A strict findings packet, with citation, repro, evidence and confidence, produces a queue people respect and act on.
- **Evals are a design input, not a QA step.** Write the eval set while you are specifying the agent, before you build it. The cases you cannot write down are the behaviours you have not actually decided yet, and discovering that after the agent works is expensive. A harness built up front lets you move quality in one direction instead of trading one regression for another. A harness bolted on afterwards mostly ratifies whatever the agent already does, because you end up writing the cases around the behaviour you can already see.
- **LLM-as-judge works, inside limits.** It holds up as a reranker and as a grader when the question is narrow and the scale is bounded, and it falls apart the moment you ask it for an overall verdict. Every judge I run scores one dimension at a time against a written rubric, and the rubric is version-controlled next to the thing it grades.
- **Ground every claim in something the reader can open.** The useful form of anti-hallucination is not a better prompt, it is a citation that resolves to a page. Pair that with a system that declines when the context is silent instead of paraphrasing around the gap. Refusal is a feature you build deliberately, not a failure you apologise for.
- **Observability on retrieval comes before prompt work.** Most hallucination complaints are retrieval problems wearing a costume. Top-K visibility and rerank-score histograms are cheap, and they resolve more of those complaints than prompt engineering does, because they tell you whether the right chunk was ever in the context to begin with.
- **Context engineering is mostly deciding what to leave out.** Retrieval decides what is available; what reaches the model, in what order, with what metadata attached, is a separate set of choices and usually the one that moved the number. Chunk on the document's own structure rather than a character count, pick the chunk boundary to match the citation unit you want to hand back, and use the reranker to make the context smaller rather than larger. For agents that outlive one window, the same rule in a different costume: durable facts go in a file that gets re-read, and a post-reset summary is a claim to verify rather than state to act on.
- **Fine-tuning sits further down the list than people expect.** I have not needed it yet. Retrieval quality, a reranker and a strict output schema have covered every case I have hit, and all three are cheaper to change on a Tuesday afternoon than a training run is. Fine-tuning mostly buys consistency of form, which is usually the problem those three already solved.
- **Run inside the user's session.** Re-implementing SSO and MFA in a headless harness is almost always a worse use of time than borrowing a logged-in browser and being deliberate about side effects.
- **Reversibility is a feature.** Backups before destructive ingest. Validate before promote. Dry runs that print the diff. Every project here has a story for rolling it back, because the ones that did not taught me to.
